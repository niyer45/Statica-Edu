# Multi-model learning loop — shared contracts (task 45.2)

Additive specification, 2026-10-17. Defines the contracts that task 34 (selection/session integration) and tracks 46–50 implement for the five original-catalog models scoped in `../original-catalog/` (D-38). It does not regenerate the completed M0–M3 requirements/design. Cantilever Beam I behavior, results, saves and tests stay unchanged; dormant Cantilever Beam II stays unregistered until task 52.

Status: specification only. No contract is implemented and no card is activated by this document. Requirement IDs are `MM-nn`. design.md supplies type sketches, compatibility analysis and the implementation/test plan.

## Identity and versioning

- MM-01 Model identity: Every analysis model has a string id and a positive integer version. The beam model is `eulerBernoulliCantileverTipForce` version 1. New ids are `circularShaftTorsion`, `sdofBaseIsolation`, `plateFinHeatSink`, `steppedBarBracket` and `pinJointedBracedFrame`; final ids are confirmed in each 4x.1. Ids are never reused for a different formulation.
- MM-02 Challenge identity: A challenge config declares `model: { id, version }`. A loaded config whose model is not registered fails loading with a schema issue (full-page boot error path or unavailable entry), never a fallback to another model. For compatibility, a config without `model` that passes the existing beam schema is the beam model version 1. All new configs must declare `model` explicitly.
- MM-03 Result identity: Every stored analysis names the model id that produced it. New-model analyses also store `modelVersion`. Beam analyses keep their existing shape, with version 1 implied, because persisted v1 results are compared key-for-key on load.
- MM-04 Version policy: A challenge version change (constants, limits, wording that changes meaning) uses a new storage key and never silently re-scores an old session. A model version change that alters any output requires a challenge version change for every challenge using it. The registry holds exactly one version per model id. Saved results naming another model version are rejected with a specific notice.

## Registry and dispatch

- MM-05 Registry: A single pure registry maps model id → model definition (config schema, design schema/validation, edit operations, analyze, evaluate, primary prediction metric, comparison metrics, explanation facts). Dispatch uses only the explicit model identity of the active challenge and the stored result. No code infers a model from field shapes, catalog discipline or card art.
- MM-06 Bundled challenges: A registry of bundled challenge configs maps challenge id → raw config, each validated by its model's loader. A catalog entry may be `available: true` only if its challengeId resolves to a bundled config that loads successfully and whose model is registered. A guard test enforces this. Dormant configs (Cantilever Beam II) may exist in source but are not linked from an available entry.
- MM-07 No substitution: Only the beam model may produce beam metrics. Unsupported or unregistered models cannot run. The UI shows the existing unavailable state and never an analysis from another model.

## Domain contracts

- MM-08 Purity and placement: Model code stays in the existing pure layers, using per-model subfolders: config types/schema in `challenge/`, design types/validation/edits in `geometry/`, analysis/applicability/constants in `physics/`, and constraints/evaluation/prediction metric/explanations in `evaluation/`. The registry that binds them lives in `state/`. Existing import boundaries, the architecture test and the no-formulas-in-UI/state rule apply to every model. The beam modules stay at their current paths.
- MM-09 Design validation and edits: Each model defines a design type, a total validator returning typed errors, and edit operations that either produce a valid design or return errors while keeping the draft unchanged (the existing clamp/strict semantics). Locked fields are defined per model and cannot change through any action or import.
- MM-10 Analysis: `analyze(design, challenge)` has the precondition of a valid design. It is deterministic, returns only finite numbers, and reports `applicable`, `warnings`, `notApplicableReasons`, `assumptions` and `unsupportedEffects`. A state with no defined numeric result (for example a mechanism) is an explicit analysis status with the undefined quantities absent, never NaN or a placeholder. Internal invariant failures throw a typed error, which the reducer turns into a notice without appending a result.
- MM-11 Evaluation: Every model returns the shared evaluation envelope: status (`accepted` | `notAccepted` | `modelNotApplicable`), accepted flag, ordered constraint results with value/limit/unit/passed/utilization, failure ids, model-specific margins and grounded facts. Accepted if and only if applicable and every constraint passes, using `withinLimit` with REL_TOL. Non-finite values never pass. An undefined-result status is `modelNotApplicable`.
- MM-12 Units: Constraint units extend the existing `m | Pa | kg | bool` with `rad`, `Hz`, `K`, `ratio` and `W/K`, all SI. Display formatting (degrees, °C, mm, g, kN/m) is a UI concern implemented once per unit, not per component. Absolute temperatures are stored in kelvin.
- MM-13 Prediction: Each model declares one primary prediction metric and its student-facing name. Scoring reuses the 0.98/1.02 ratio classification. If either side lacks a finite positive primary metric, the outcome is recorded as not scorable (no direction, no match) and stored as such. The beam outcome shape and Requirement 14 behavior are unchanged.
- MM-14 Comparison and explanations: Each model declares its comparison metrics (stored-value deltas only) and explanation-fact generators that satisfy the existing grounded-facts rule (every number in text comes from a stored basis value). History/compare/My designs show model-declared metrics; no beam metric labels appear for other models.

## Session, persistence and import

- MM-15 Session shape: The shared session holds the existing learning-loop fields (mode, draft, draftStatus, draftErrors, history, deletedIterationIds, pendingPrediction, compareSelection, reflectionAnswer, submission, ui), parameterized by the model's design/result types. Shared reducer actions (prediction, runTest, deleteIteration, restore, toggleCompare, reflection, submit, importDesign, reset) behave identically for every model. Model edits use the model's edit actions. Beam edit actions remain valid for the beam only.
- MM-16 Isolation: Each challenge has its own session, store instance and storage key `ei:session:<challengeId>:v<version>`. Opening, switching, resetting or failing to restore one challenge never reads, writes or clears another challenge's state. Mode remains selected before entry per challenge (D-37).
- MM-17 Beam save compatibility: Existing Cantilever Beam I storage keys, v1 envelopes and v1 design exports continue to load, and beam sessions continue to serialize as v1 envelopes, byte-compatible with the current format, so a rollback to the current release does not discard them. Existing persistence tests remain unchanged.
- MM-18 New-model persistence: New-model sessions use envelope schemaVersion 2, which adds `model: { id, version }`. Validation re-validates every design, re-analyzes and re-evaluates every result with the registered model, rejects any numeric mismatch beyond 1e-9 relative, verifies prediction outcomes and checkpoint coverage, and accepts all-or-nothing. A v2 envelope for a beam challenge, or a v1 envelope for a non-beam challenge, is rejected.
- MM-19 Design import/export: Beam keeps `ei-design` schemaVersion 1. New models export `ei-design` schemaVersion 2 with `model`, `challengeId` and `design`. Import rejects a different challenge id, model id or version, forbidden keys, oversize text, unknown keys and locked-field changes, and returns a design built only from validated fields. A failed import leaves the session unchanged.

## UI contracts

- MM-20 Model UI slots: A UI registry maps model id → controls, primary visualization (may be lazy), main-bundle fallback (SVG/text, independent of Three.js), result summary and comparison rows. Shell, workbench layout, dialogs, history, reflection/submission, toast/live region and mode selection stay shared and are not duplicated per model.
- MM-21 Guided content: Guided step instructions and hints are per-challenge content, validated with the challenge config and redacted like the challenge. Phase recommendation stays shared and derived from session state. Parametric context text is per challenge. No content may reveal the reference design or invent numbers.
- MM-22 Accessibility: Every model's controls have accessible names and numeric/keyboard alternatives to any pointer interaction. State is never conveyed by color alone, and charts/visualizations have table or text equivalents. The single live region and serious/critical axe gates apply. Layout works at 320 px.
- MM-23 Shell attribution: Library availability, challenge details, My designs and workspace-started detection are per challenge. My designs attributes each workspace card to its challenge title and never mixes histories. Unavailable entries keep the existing "Not available yet" behavior.
- MM-24 Test-only exposure: The dev snapshot (`__EI_STATE__`, dev port only) reports the active challenge id and its session. The production build exposes nothing.

## Verification obligations

- MM-25 Regression: All existing Cantilever Beam I unit/property/component/E2E tests pass unchanged, except tests that assert single-challenge shell internals and must be updated to the multi-challenge contract with equivalent or stronger assertions. Coverage thresholds stay the same or rise.
- MM-26 Contract tests: Registry/catalog guard tests; dispatch-by-identity tests (an unknown or mismatched model is rejected); persistence isolation across two challenges; v1 beam envelope fixtures that load byte-for-byte; v1/v2 cross-rejection; import cross-challenge/model rejection; not-scorable prediction; generic reducer properties (append-only, snapshot isolation, prediction/submit gating, purity) run against the beam and at least one non-beam test model.
- MM-27 Test model: Until the first real model lands, contract tests may use a test-only model registered only in test code, never bundled or linked from the catalog.
